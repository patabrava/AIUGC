# Bridgecode 4.3.2

At each new task, read this entire file; load each triggered `bridgecode/` specialist completely before its governed action. After compaction or a model change, recover this core, active work, relevant architecture, and required specialists before continuing.

## Operating contract

Bridgecode is a repository-local decision and delivery policy. The agent and available harness perform the work; the CLI installs and verifies instructions. Apply this policy within the host's instruction hierarchy, permissions, and the user's scope. Installed Bridgecode instructions are package-owned; project memory belongs in `agentic/`. Distinguish the requested Task, actual State, observed Evidence, and available Executor. The contract consists of the authorized outcome, constraints, preserved behavior, and acceptance criteria. Memory guides inspection; current code and applicable evidence establish what is true.

## Judgment and routing

On every turn, apply or revalidate all three Best-Agent moves: recognize intent, select the perspective or smallest useful amalgam, and anticipate supported corrections. Establish the intended outcome and bounded definition of done; inspect relevant evidence; test the assumption whose failure could invalidate the approach; choose the best-supported perspective or smallest useful amalgam; and repair foreseeable mistakes supported by the brief. A perspective has a Person, a transferable Core, and a Magnum Opus or defensible representative work. Connect the Core to demonstrated decisions, transfer conditions, limitations, and concrete choices here. Amalgams give each perspective a distinct responsibility and a conflict rule. Attribution must be defensible; a name supplies no authority. Scale selection to consequence: it must improve decisions rather than decorate routine work. Preserve explicit requirements when inferring intent. Research unknown facts yourself; ask only for unresolved user-owned decisions or requested checkpoints.

Choose ROBUST when consequential uncertainty, interacting boundaries, unfamiliar mechanisms, design direction, migrations, or costly failures require deeper investigation and coordination. Choose LEAN when the goal, mechanism, affected contracts, and validation are sufficiently known. LEAN profiles are PATCH (scoped change), DEBUG (evidence-led repair), and ASSESS (read-only judgment). Size and labels are examples, not routing criteria. A targeted current-doc lookup does not alone require ROBUST; escalate when what it reveals changes the contract or makes compression unsafe. Two failed focused repairs require reassessment of the cause and route, not another identical attempt.

**Every-turn entry gate.** Start the first public response with `BRIDGECODE_ROUTE: ROBUST` or `BRIDGECODE_ROUTE: LEAN / PATCH|DEBUG|ASSESS`. Briefly state what research, Q&A, plan, execution, review, and condensation will do or skip, with a reason for the route and each stage. Immediately say that the developed decision brief, stage work, checklist, and done criteria will live in `agentic/analysis.md`. Before task-directed research, questions, implementation, or deliverables, create or refresh that board: its first content block applies all three Best-Agent moves with a developed operational rationale connecting intent/acceptance, perspective/Core/representative work and transfer conditions, and supported anticipatory corrections. This brief governs subsequent work. Necessary instruction loading and safe reading of existing memory may precede the write; evidence-dependent choices remain provisional. Then research and refine the same block, ask any unresolved questions, finalize the checklist, and execute the authorized route. Revalidate all three moves on follow-ups, updating in place before dependent actions. Record decisions, assumptions, and evidence summaries, never private deliberation. Read-only/no-file-write requests use a compatible visible decision brief instead and explain that no board is written; exact-output constraints take precedence where no compatible progress channel exists. Disclose unavailable storage and use the visible brief without claiming a file write.

## Shared process

**Research.** Inspect the prompt, relevant `agentic/architecture.md`, active work, affected code, callers, contracts, and validation paths before choosing a mechanism. For ROBUST or consequential ambiguity load `bridgecode/best-agent.md`. Scale from repo evidence/direct probes to current canonical sources for unfamiliar, external, version-sensitive, security, legal, platform, or otherwise unstable behavior. Test assumptions that could invalidate the task, preserved behavior, or supported-path safety; stop when the next action is trustworthy and further investigation would not change implementation or acceptance. Familiar stacks are a preference only when they fit; otherwise prefer inspectable primitives/platform capabilities and research what reliable knowledge cannot settle. Keep reusable notes only when they prevent repeated necessary investigation. Separate fact, inference, and unresolved assumption.

**Q&A.** After research, ask one or two high-level questions only where meaningful user choices remain. Compare perspectives or the smallest useful amalgams: Person, Core, representative work, distinct responsibilities, concrete consequences, and fit to the user's intent. Describe practical consequences plainly so the user can choose without knowing the people. Recommend the best-supported match, allow a custom answer, and preserve prescribed direction. The chosen Core governs downstream details; ask further questions only for specific consequential gaps it cannot settle. Prefer the native question-card tool (`request_user_input_async` when available), with self-contained questions and concise recommended-first options. Continue independent authorized work while awaiting answers; dependent actions wait. Use another supported question interface or concise prose when unavailable. Requested checkpoints apply in either route; ROBUST otherwise continues when decisions and authorization are sufficient.

**Analysis and plan.** After the entry gate and research/Q&A, refine `agentic/analysis.md` with one current decision brief and one checklist; keep the three-move block first. Connect goal, inspected state, evidence, user decisions, perspective transfer conditions, chosen mechanism, preserved contracts, non-goals, and assumptions. Each item states required outcome, affected boundary, observable proof, and status. Freeze this acceptance contract before implementation; change it only for new user instructions or concrete evidence that invalidates it, recording why rather than turning a preference into a requirement. Production-grade means proportionate correctness, resilience, clarity, operability, security, accessibility where applicable, and real validation; it does not require a framework, service count, or speculative feature. Prefer a repo-fitting vertical slice with adjacent interface, logic, schemas, validation, errors, tests, and operational notes. Start simple; new services, queues, jobs or shared packages need demonstrated isolation, scaling, reliability, compliance or operational demand. Plan the smallest sufficient regression block and an explicit stopping condition. ROBUST develops the evidence; LEAN compresses the same obligations. Exact answers and read-only assessments need no repository writes. Preserve other active tasks and their owned sections.

**Execute.** Implement the complete authorized checklist as coherent work. After tracing the affected flow and callers, stop at the first adequate option: existing behavior/configuration; reuse in this repo; standard library; native platform feature; suitable installed dependency; smallest justified new code. A simpler mechanism must still satisfy explicit requirements. Prefer deletion or inlining of unnecessary indirection over new abstractions; extract shared behavior after demonstrated repeated need (the rule of three is a reuse heuristic, not a quota). Fix an evidenced root cause once at the responsible boundary rather than adding sibling symptom patches. Preserve established conventions; keep coherent files compact but complete, splitting for productive comprehension rather than arbitrary LOC or tiny-file proliferation. Keep dependencies minimal, one primary tool per concern where viable, specialized behavior behind thin edge adapters, and domain logic locally readable; avoid implicit globals, reflection-heavy critical paths, speculative configuration and generic utility layers. Keep infrastructure clients/factories narrowly scoped and free of domain logic. Define changed boundary contracts before implementation, validate entry inputs, shape exits, keep uniform status/code/message/optional-details errors without leaks, protect secrets, and retain required security, accessibility, data-loss handling and real-world calibration. Use deterministic repo-native install/develop/test/build/start commands, required dependency pins, and short runnable instructions. Make logs useful at boundaries/errors/critical state changes, with correlation IDs across boundaries where needed and no sensitive data. Diagnostic probes/compiler feedback may guide development. Document a deliberate limitation only when it is real and relevant, with its trigger for reconsideration. Avoid future scaffolding, duplicate tools, unobservable failures and habitual stack choices. Stop adding code when the accepted behavior and proportionate proof are present.

**Acceptance and review.** Run one coordinated real regression block after implementation against the stable contract. Exercise production functions, contracts, adapters or user flows; combine unit, contract, integration and end-to-end checks only where the affected path needs them. Frontend checks use the running app through browser/computer interaction with relevant states, accessibility, responsive behavior and console health. Startup alone is insufficient. Preserve durable checks in the repo's established location, preferably adjacent to their feature; avoid tests that merely mirror trivial reversible edits. After changes/failures, rerun affected checks plus proportionate regression coverage; repeat the entire block when shared boundaries or uncertainty warrant it. Passed checks need no repetition or broadening without new changes, failures or concrete unresolved concerns.

**First review.** After implementation and relevant tests pass, spawn one fresh native reviewer using the same active model and reasoning effort as the implementing root (`fork_turns: "none"`), read-only with no inherited conversation. Use native inheritance when the tool contract guarantees matching settings and no routing override changes them; otherwise explicitly match verified active settings. Do not infer active settings from unrelated defaults. Supply the stable acceptance contract, chosen mechanism, final diff, all relevant surrounding code/architectural context, concise test evidence, known limitations and exclusions. Context must be sufficient for confident judgment; exclude irrelevant material, not essential evidence to save tokens. Before raising a finding apply the relevance gate: identify a concrete defect, its evidence/reachable supported path, and the acceptance requirement or preserved correctness/security/data-safety/accessibility invariant it blocks. Root-cause or disproportionate-mechanism findings must pass that same gate; small diffs alone prove neither quality nor a defect. Omit optional improvements, speculative edge cases, unrelated defects, style preferences, future-facing concerns and newly imagined requirements. An evidenced edge case on a supported path remains relevant. Stop inspection once enough evidence supports the verdict. Response: exactly `PASS`, or begin exactly `FIX`/`REPLAN` with roughly 5000 tokens or less of dense actionable rationale, file/line references and repair direction where applicable, and only the minimal code/interface/algorithm/pseudocode kernels and adaptation guidance needed to communicate the core correction; no full patches, edits, exhaustive implementation or child agents. `FIX` means concrete blockers with a proportionate mechanism. `REPLAN` means evidence that the mechanism itself is disproportionate/structurally wrong, or a coherent repair cannot remove the structural cause without interacting special cases. A first `PASS` ends independent review; root verifies acceptance and finishes.

**One correction stage, then terminal review.** A first `FIX` or `REPLAN` opens exactly one correction stage. Group related findings by root cause. For FIX, make one coherent correction; for REPLAN, stop incremental patching, compare the current mechanism with a simpler viable alternative, revise plan/contract only as the evidence requires, and implement the revised mechanism. The implementing root remains model-agnostic. Rerun affected tests and proportionate regression. Then spawn exactly one fresh native final read-only reviewer using the same active model and reasoning effort as the implementing root with the same relevance gate/context contract plus the first verdict and correction/replan evidence. Require exactly `PASS`, otherwise `UNRESOLVED` followed only by remaining blocking defects, concrete evidence/file-line references where applicable, and missing evidence or user guidance where needed. The final reviewer never returns FIX/REPLAN or requests another correction/review cycle. Root verifies acceptance on PASS; UNRESOLVED stops further implementation and review in this cycle and is reported plainly. If root verification contradicts PASS, report UNRESOLVED rather than claiming completion. Never spawn a third implementation reviewer, perform another reviewer-triggered correction pass, or restart planning for the same cycle unless a new user instruction explicitly begins a new cycle. Persist cycle identity, phase, first verdict, correction-stage usage and terminal status in active memory across follow-ups/compaction; a resume or rate-limit retry does not reset the budget. Tool failure/timeout is not a verdict: disclose and preserve the pending phase; retries may recover that same failed invocation, not add substantive review rounds. If matching native review is unavailable, report incomplete review and seek user direction rather than silently substituting a model, external API or simulated PASS.

**Condense.** Every completed flow checks memory; write only within authorized scope. Merge verified responsible files/symbols, contracts and regression protection into `agentic/architecture.md`; update stale ownership/flow descriptions and retain genuine unencodable constraints as scoped notes. Code corrections belong in the authorized implementation/correction stage, with architectural change when the cause is structural. Condensation is documentation and cleanup, not another improvement pass: do not invent a refactor to produce a lesson, reopen a completed review cycle, or encode speculative future needs as binding rules. A newly noticed concrete blocker is reported under the terminal policy. Keep reusable tests, remove disposable probes, and preserve unresolved recovery state. Read-only work reports proposed memory changes without applying them.

## Engineering, writing, and memory

Engineering principles are applied at the stage where they govern a decision: investigate evidence before choosing, bound the contract before building, prefer local sufficient mechanisms while implementing, and accept or stop on relevant proof. Both routes use these shared gates; proportionate depth changes, the required outcome does not.

Match writing to the subject, audience, purpose, and required form. Explain through connected prose; use structure for real steps, comparisons, and reference material. State the outcome early, preserve exact terminology and source meaning, explain useful technical terms plainly, and remove filler without deleting necessary relationships. Keep harness/reviewer packets dense and explicit. Apply Taste only to meaningful discretionary choices; honor fixed requirements. Write product interfaces from the user's goals, actions, states, and recovery needs; omit irrelevant development internals. Never fabricate proof, functionality, attribution, or validation.

`agentic/analysis.md` is a temporary task board: the first-block three-move brief, current checklist, evidence, remaining steps, review cycle/phase/status, and next action. On entry, resume the same unfinished objective by updating its state in place; replace completed stale state when starting a new objective. Keep paused/blocked work recoverable and preserve genuinely concurrent unfinished tasks in identified owned sections, each with its three-move brief first. At completion, prepare the handoff, check condensation, merge only durable knowledge into architecture, and remove the completed task's section; delete analysis.md when no active work remains. Every turn checks this lifecycle. Do not append turn logs or completed-task histories. `agentic/architecture.md` is the durable map: short system overview, annotated maintained-file tree, ownership/data flow, key constraints and corrections beside responsible files, and run/test entry points. Group generated/dependency/cache trees; inspect relevant source to verify freshness. `agentic/design/DESIGN.md` describes verified implemented design; references preserve visual intent. Keep production assets at one explicit runtime location and check usage before cleanup. Retain reusable tests where the repo expects them. Delete disposable probes and simulations after useful evidence is incorporated; retain failure recovery material until recovery succeeds.

Every handoff identifies `agentic/architecture.md`, the active checklist, current status and evidence limits, exact relevant files/symbols, required specialists, unresolved decisions, and next action. Read relevant source rather than rediscovering the whole repo. On upgrade, transfer every recognized repo rule into `agentic/architecture.md`, preserving its meaning and implementation status; retain unrelated AGENTS.md blocks after the Bridgecode core in their original relative order. Unresolved rules remain binding and clearly marked unverified in architecture.md. Before affected work, inspect applicable constraints and verify them against code/tests. Urgently reconcile imported rules: merge implemented constraints beside their responsible files and retain unresolved requirements there until authorized corrections are verified. Never discard an unmapped rule or infer that relocation implements it. Preserve existing architecture; migration authorizes no unrelated refactors. AGENTS.md has no Bridgecode-imposed size gate.

## 9) Specific harness rules (Codex)

- Every turn must classify the request by task signal, choose the Bridgecode route from the task-signal table, and expose the route with `BRIDGECODE_ROUTE: <task signal> → [GENERAL, ROUTE...] | MODE: <mode> | WHY: <one sentence>` before major action and once in the final handoff when a handoff is produced.
- Browser diagnostics must use a separate tab, preserve the operator's active workflow tab, and close or restore every internal JSON/status endpoint tab before handoff so diagnostic state cannot be mistaken for an application crash.
- When inspecting environment files, print only explicitly allowlisted non-secret keys and derived credential metadata; never emit raw `.env` line ranges or credential payloads into harness output.
- Run migration-history fetches in a verified isolated workspace; validate the workspace before invoking the CLI and abort dependent commands on setup failure. Apply only the approved migration and preserve unrelated hosted history and local migration files.
- For local compose smoke tests, set `APP_ENV_FILE` explicitly before recreating services; long-lived containers may retain a retired provider/project identity, and a missing legacy worker image must not prevent recreating the active web/video/image services. After starting Docker, immediately inspect auto-restarted local app and worker containers for hosted-database connections and stop conflicting consumers before isolated validation. Before live production validation, compare local queue consumers with the deployed contract and stop conflicting development workers connected to the production database; a local image worker must never finalize production jobs with an unreleased visual contract.
- Database diagnostics must exclude statement-history views and commands such as `inspect db outliers` or `calls` when SQL literals can contain temporary credentials; use lock, blocking, duration, and aggregate health views with redacted statement text.
- When the harness sandbox read-denies credential-named files (for example `google/auth/credentials.py` or `.env`), suites that import google.auth, botocore, `app.main`, or `get_settings()` cannot collect. Build new slices with lazy provider imports and injected settings, clients, and storage so their focused tests run inside the sandbox; report blocked suites as not run and ask the operator to run them instead of weakening the sandbox.
